## Verified bb / bb.js facts (main agent, homelab, bb 5.2.0 = `5.2.0-nightly.20260807`)

- `bb prove --scheme ultra_honk -b <bytecode> -w <witness.gz> -k <vk> -t <target> -o <dir>` writes `proof` + `public_inputs`. `-b` accepts either the compiled JSON artifact or the raw gzipped ACIR (base64-decoded `bytecode` field). Both produce identical output.
- **Without `-k` the CLI fails** (`Unable to open file: ./target/vk`), also with `--vk_policy recompute`. `--write_vk` without `-k` succeeds and additionally writes `vk` + `vk_hash`.
- Timings on yacana W (12 threads): `-k` 1.22 s; `--write_vk` 1.48 s; `write_vk` alone 0.52 s; `verify` 7 ms. Same proof bytes with 4 threads.
- Proof sha256 `57799830…` equals yacana's committed fixture proof (WASM-produced per the elixir spike I8): native == WASM byte-identical, reconfirmed here.
- VK for `noir-recursive` and `noir-recursive-no-zk` is byte-identical (ZK is a prover setting, not a VK property).
- Malformed inputs fail closed with exit 1 and no output: 4 corrupted VK bytes (default and `check` policy) → field deserialization error; random VK → same; random bytecode → `Invalid gzip data`.
- `HARDWARE_CONCURRENCY` env caps threads (`num threads: 4`).
- CRS: bb reads/fetches `~/.bb-crs` (`-c/--crs_path`); the box already has 3.1 GB there from chonk use. UltraHonk for W needs only the bn254 G1 prefix chonk already pulled.
- **Zero public inputs → bb writes an EMPTY `public_inputs` file (0 bytes)** and still verifies (probe circuit `nopub`, aztec-nargo 1.0.0-beta.25 + bb 5.2.0). `validate_proof_len` (non-empty check) must not be applied to public inputs.
- **`bb verify` exit codes**: 0 + `Proof verified successfully` on success; **1** + `Proof verification failed` on a tampered proof; 1 + `invalid proof size. Expected 458, got 410` on a zk/no-zk target mismatch. Exit code alone cannot separate "invalid proof" from "bb failed"; a verify route must parse the output line.
- Probe fixture `square` (`fn main(x: Field, y: pub Field) -> pub Field { assert(x*x == y); std::hash::pedersen_hash([x, y]) }`): 19 ACIR opcodes, circuit_size 28,680, proving key 34 ms, `public_inputs` 64 B, proof 13,120 B (`noir-recursive-no-zk`). `Poseidon2` is no longer in Noir std at beta.25 (external `poseidon` lib); pedersen is. Artifact 90 KB, witness.gz 211 B.
- Proof/VK sizes depend on the target's hash family: `evm` → proof 8,384 B (262 fields), vk 1,888 B; `noir-recursive-no-zk` → 13,120 B (410), vk 3,680 B; `noir-rollup-no-zk` (IPA) → 15,360 B (480), vk 3,680 B. All 32-byte aligned. VK is identical between zk and no-zk variants of the same family, different across families. Proof size is independent of circuit size (W and `square` both 410 fields).
- bb.js 5.2.0: `new UltraHonkBackend(acirBytecode: string /* base64 */, api: Barretenberg)`; `generateProof(compressedWitness: Uint8Array /* gzip */, {verifierTarget}) → {proof: Uint8Array, publicInputs: string[] /* "0x"+64 hex */}`; `verifyProof` recomputes the VK in WASM each call; `getVerificationKey()` → `Uint8Array`; `Barretenberg.new({threads?})`. `ProofData` type lives in `@aztec/bb.js` `proof/index`.
- The yacana miner (`~/Projects/elixir/packages/miner-core/src/work.ts`) uses `@aztec/noir-noir_js` 5.2.0 `Noir.execute` + `@aztec/bb.js` 5.2.0 `UltraHonkBackend(artifact.bytecode, api)`, `generateProof(witness, {verifierTarget: 'noir-recursive-no-zk'})`.

## Version negotiation (mapper C, condensed)

- The SDK sends its own `@aztec/stdlib` pin as `x-aztec-version`; the app resolves it by exact string match to the bundled sidecar or a marker-verified cache dir (`~/.presto/versions/<v>/bb`), downloading `barretenberg-<arch>-<os>.tar.gz` from the `aztec-packages` release tag `v<v>` on demand. No floor, no "closest" logic, empty revocation list.
- **Aztec version == `@aztec/bb.js` npm version == bb release tag by construction** (`copy-bb.ts:228-235` resolves the sidecar version from the installed `@aztec/bb.js` `package.json`; `version_policy.rs:240-249` documents the header as an Aztec version). No field anywhere records a distinct bb build id; `bb --version` is never spawned (`version_policy.rs:292-294` calls it future work). Consequence: the "bb mapping" Alejo asked for is an identity today — a Noir dev's `@aztec/bb.js` version string IS the value to send.
- `api_version` is exact-equality gated on the SDK side; bumping it makes every existing SDK see the app as absent (WASM fallback). Adding fields is safe everywhere (four allowlist validators, no closed-shape test).
- `available_versions` drives the SDK's client-side `needsDownload` prediction only; the server's `needs_download` never crosses the wire.

## Collision / dedup risks

1. `probe.rs:51-54` hardcodes `api_version == 1` for redundant-instance detection — a naive bump misses it.
2. SDK `PRESTO_API_VERSION` exact equality — a bump without a lockstep SDK release strands every installed SDK on WASM.
3. `prove()` inlines ~150 lines of guard sequencing with no seam; a copy-pasted second handler will drift on the next security fix. Extract a guarded prelude or a scheme-parameterized handler.
4. `bb::prove` prepends the 4-byte header unconditionally — the UltraHonk path needs a sibling function.
5. Tempdir prefix `prove-` is shared by both schemes — fine for the reaper, disambiguate only if diagnostics need it.
6. `bbWorkerPlugin` resolves bb.js via `@aztec/bb-prover`; a second `@aztec/bb.js` copy in the playground tree would serve the wrong workers — keep one resolved copy (`resolve.dedupe`).
7. First `peerDependencies` in the repo reverses the SDK's F13 "deps not peers" decision — must be an explicit, documented choice; the tarball-consumer assertions do not transfer.
8. `packages/presto/core` (Rust crate) vs `packages/presto-core` (npm) — the word "core" is overloaded; docs must disambiguate.
9. `@aztec/noir-noir_js` is not in the lockfile; adding it triggers the bunfig excludes parity test and the 7-day min-age gate on first non-frozen install (it is `@aztec/*`, so it must be added to the excludes list).
