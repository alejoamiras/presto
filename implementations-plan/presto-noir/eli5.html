Presto Noir

Teach Presto to prove any Noir circuit natively, not only Aztec transactions — so the yacana web miner and Noir dApps get the same 5× speed-up the Aztec SDK already enjoys, through a drop-in replacement for the bb.js backend they use today.

What this is, in plain words

Presto today does one job: when an Aztec dApp needs a transaction proved, the browser hands the work to the Presto app on your machine, which runs the real Barretenberg prover instead of the slow browser version. That path is called "chonk" and it only understands Aztec transactions.

A Noir circuit is a different, simpler shape of proof ("UltraHonk"): one program, one set of inputs, one proof. The yacana miner proves the same small circuit over and over; each proof is a lottery ticket, and the native prover buys tickets five times faster. Today Presto can't help it at all.

The plan adds a second door to the app for exactly this kind of proof, moves the shared "talk to Presto" plumbing out of the Aztec-only package into its own small package, and ships a new package that Noir developers can swap in with two lines. Nothing about the existing Aztec path changes.

What was checked before planning

  • The speed-up is real and the proofs are identical. On this machine the native prover does the miner's circuit in 1.2 s versus 6.3 s in the browser engine, and the bytes match exactly — so switching provers never changes a mining ticket.
  • The prover needs the verification key up front. Without one it refuses to run; the plan lets the client send it (fast) or asks the prover to compute it (a quarter second slower) and hands it back for next time.
  • Circuits with no public outputs produce an empty output file, which the existing validator would have rejected. Caught by review, fixed in the design.
  • Only the "no-zk" proof flavours are reproducible. The zero-knowledge flavours add randomness, so "byte-identical" claims are limited to the flavours where it's true. The miner uses a no-zk flavour.
  • Bad inputs fail cleanly. Corrupted keys, random bytes, and a key from the wrong circuit all make the prover stop with an error or produce a proof that simply doesn't verify. No crashes, no hangs.
  • The trust boundary does not move. An approved website already controls the bytes the prover parses. The new door sits behind the same approval popup, the same size caps, the same timeouts.

Things worth knowing before you decide

  • The "which bb version" question turned out to be an identity. The Aztec version, the bb.js package version, and the native prover's release tag are the same string by construction. The health check will still expose a mapping table, but today every row reads "5.2.0 → 5.2.0". Question 7 below lets you drop it.
  • bb.js already goes native in Node. Presto's value for Noir is the browser (and Windows, where bb.js ships no native binary). That's where the miner lives.
  • Mining runs your machine at full tilt for hours. This plan keeps the cheap guards (one prover at a time, per-site queue cap, revocation applies to queued work, thread cap from the speed setting). The tray meter and one-click revoke are a separate follow-up plan, as you asked.
  • Old apps degrade gracefully. The Noir package sees an app without the new door and quietly uses the browser engine. The Aztec SDK is untouched in both directions. No protocol version bump.
  • First time this repo declares a peer dependency. The Noir package rides on the bb.js the developer already has, rather than bringing its own copy. The Aztec SDK deliberately chose the opposite earlier; the plan explains why this case differs.

Decisions taken at the gate

  • 1. Native verification and key computation: later. v1 keeps them in the browser engine; "native only" applies to proving.
  • 2. bb.js pin: exact 5.2.0. Both new packages start at 1.0.0 with ordinary semver.
  • 3. Presto version carrying the new door: 1.1.0.
  • 4. Per-site queue cap: four (half the total).
  • 5. Security hardening pass: yes, before the first stable publish of the Noir package.
  • 6. yacana origin for the verified badge: https://yacana.network (apex only; preview deployments never get the badge). A recognition badge, not pre-approval.
  • 7. Health-check mapping table: keep it.
