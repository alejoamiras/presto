Executive summary

The presto-noir work added a second proving route to the Presto desktop app, a shared transport package (@alejoamiras/presto-core), a bb.js drop-in adapter (@alejoamiras/presto-noir), a playground panel, and a three-package npm release path. Six clusters were audited by two model families independently, each side then challenged the other's report, a coordinator deduplicated and banded the result, and two fresh verifiers re-derived every finding from source. Two clusters — the Noir adapter and the playground panel — came back clean from all four passes. The request path from a web page into the native prover held up against forged hosts, missing origins, revoked approvals, decompression bombs, and malformed keys.

Five findings survived. The one High is in the release pipeline, not the product: the CI job that publishes the three packages with signed provenance runs a fresh npm install from the public registry, with install scripts enabled, before it publishes the file it already packed. A compromised upstream dependency that coincides with a release could swap the artifact and ship it with a valid signature. Two Medium findings: in the shared client, two overlapping proofs can share a protocol decision so one private witness is sent to the plain-HTTP port that was never health-checked (only with a non-default downgrade setting); and in the app, a request header drives multi-gigabyte downloads and cache bookkeeping before the request proves it is a real job, so one approved website can force unbounded download churn and hold the cache above its size cap. Two Low items: the playground deployment does not tie the file it deploys to the provenance it verified, and caller-supplied code can run after the client's last policy check (informational).

Recommended order: land the High's interim mitigations today and the CI job split this week; fix the two client findings together in presto-core before promoting the packages to latest; then the download budget in the app; and the playground digest check alongside the High, since they are the same missing-digest pattern.

Cheapest fixes first. F-005 (move one line above a check, under an hour), F-004 (hash the packed file and compare it to the verified attestation, hours), F-002 (build the URL from the protocol that passed the check instead of reading it live, hours). F-001's interim mitigations (--ignore-scripts, an exact typescript pin, a digest asserted before publish) are also hours and should go in the same first PR.
Ship together. F-001 + F-004: both are "verified one thing, consumed another" gaps in the release path; the fix is the same discipline (compute a digest at the trust boundary, assert it at the sink). F-002 + F-005: both are checks in PrestoClient.prove() that can be outrun by something else touching shared state; one immutable per-attempt snapshot closes both.

Findings

High F-001 Registry-resolved code runs inside the OIDC publish job and can rewrite the artifact published minutes later
Found by Claude+Codex confidence: high CWE-829 · CWE-269 fix: hours (interim) · ~1 day (job split)

What it is. When Presto's SDK packages are released, a GitHub Actions job builds the package, packs it into a tarball, and publishes it to npm with a cryptographic "provenance" statement that says "this exact file was built by this exact workflow." Between packing and publishing, the same job runs a "consumer test": it installs the package the way a downstream user would, which pulls fresh copies of its dependencies from the public npm registry and lets those dependencies run install-time scripts. That install happens inside the job that holds the signing credentials, and the path to the not-yet-published tarball is sitting in the job's environment.

What an attacker would do. Compromise any package in that dependency tree (the May 2026 @tanstack/* worm did this to 42 packages in six minutes) and wait for a Presto release. Their install script reads the tarball path from the environment, overwrites the file with a trojaned copy, and exits cleanly. Minutes later the job publishes the trojaned file with a valid provenance signature. Every downstream check, including Presto's own verification scripts, verifies what was published, so they all pass. Every app that installs @alejoamiras/presto, presto-core, or presto-noir then ships the attacker's code, and the provenance says it is legitimate.

The fix. Never run registry code in the job that signs. Pack the tarball, record its hash, and upload it as a workflow artifact before anything from the registry runs; do the consumer test in a separate job with no publishing rights; have the publish job download the artifact, check the hash, and publish. The repository already has the unprivileged shape: the per-package PR gate runs the same consumer script in a job with read-only permissions. Same-day stopgaps: --ignore-scripts on the installs, an exact typescript version, and a hash taken at pack time and asserted right before publish.

Medium F-002 Concurrent proofs share the protocol pin: a witness can be sent to the never-validated HTTP port
Found by Codex (Claude verified) confidence: high (mechanism) · moderate (browser timing) CWE-362 · CWE-200 fix: hours

What it is. A "witness" is the private input to a zero-knowledge proof: the secret the proof is about. The shared client sends it to the local Presto app over HTTPS, and only if the app explicitly allows a downgrade will it fall back to plain HTTP, and even then only after checking that the HTTP port answers Presto's health check. The client keeps one shared "which protocol are we using" setting. When two proofs run at the same time and the first one hits an HTTPS network error, it switches that shared setting to HTTP while it goes off to health-check the HTTP port. The second proof, already past its own checks, reads the shared setting at the moment it sends, and posts its witness to the HTTP port that nobody has checked yet.

What an attacker would do. Same-machine, lower-privilege software (a browser extension cannot do this; a local process can) listens on Presto's HTTP port. It cannot pass Presto's health check, so the normal downgrade path never talks to it. It only needs the app configured with allowInsecureDowngrade and two overlapping proofs, then it triggers an HTTPS failure (or waits for one). The second proof's witness arrives at its port in the clear. The documented boundary already accepts that a fake Presto can pass the health check by mimicking its shape; this path is strictly worse because the fake does not even have to answer.

The fix. Decide the destination when the check passes, not when the request is sent. The client already snapshots the request and re-checks a "generation" counter to catch mid-flight reconfiguration; extend that pattern so the protocol is part of the snapshot, build the URL from the snapshot via the transport's existing explicit-protocol helper, and make the downgrade bump the generation. Requires the non-default {httpsOnly:false, allowInsecureDowngrade:true}; both shipped adapters reach this code.

Medium F-003 x-aztec-version drives unbounded download churn and defeats the cache size cap before the payload is validated
Found by Claude+Codex confidence: high (mechanism) · moderate (disk-fill magnitude) CWE-400 · CWE-770 fix: hours (digest-first, re-arm) · ~1 day (download budget)

What it is. Presto can prove with many versions of the bb prover binary; a website tells it which one it needs through a request header, and Presto downloads that version (about 64 MB) on demand into a cache with a 2 GB cap and a cleanup that evicts versions not used recently. Two things happen in the wrong order. First, the download and the "this version was just used" bookkeeping run before Presto has looked at the request body, so a garbage request still costs a full download. Second, Presto fetches the whole tarball before it fetches the digest it will check it against, so when GitHub's anonymous API limit is hit (60 requests per hour), every request for an uncached version downloads 64 MB and throws it away.

What an attacker would do. A website the user has approved once (or any local page, if the headless server auto-approves localhost) sends a stream of cheap, malformed requests, each naming a real historical Aztec version. Presto downloads a fresh 64 MB tarball per request, indefinitely, burning the user's bandwidth, RAM, and disk. Separately, the page fills the cache with real versions and then keeps "touching" them every few minutes; the cleanup runs once, sees everything as recently used, and does not run again, so the cache stays above its cap until Presto restarts. Presto's concurrency caps do not help: they bound how many proofs run at once, not how many downloads happen per hour.

The fix. Fetch the digest before the tarball and fail fast. Add a download budget (one uncached download at a time globally, plus a small per-website allowance per ten minutes) that counts every attempted miss, including failures and repeats, and answer over-budget requests with the existing "try again later" code the client already understands. Re-arm the cleanup while versions stay active, or only mark a version as used once a real job reaches the prover.

Fix: (1) digest before tarball in download_bb; (2) a global single-flight + per-origin token bucket (e.g. 3 new versions per 10 min) counting every attempted miss, returning the existing 503/transient the client classifies (presto-client.ts:541-550), with duplicate in-flight downloads coalesced; (3) re-arm cleanup_after_active_window while deferred_by_active_window holds, or refresh .last-used only once a job reaches run_ultra_honk; (4) optionally run decode_and_check before acquire_prover on /prove/ultra-honk (the current ordering is deliberate, implementations-plan/presto-noir/plan.md:135).

Low F-004 Playground deploy consumes a tarball that is not bound to the provenance it verified
Found by Codex (cross-model disagreement on realism) confidence: moderate CWE-345 fix: hours

What it is. Before the playground site is deployed with the freshly published SDK, a script verifies the SDK's provenance (the signed statement about where it was built) and its registry signatures. It then downloads the SDK a third time, separately, and deploys that copy. Nothing ties the copy it deploys to the copy it verified; the only check is that the download matches whatever the registry says the hash should be at that moment, which is the registry vouching for itself.

What an attacker would do. Someone who can make the registry (or the network path to it) answer differently to three requests for the same package version within one CI job: serve the real package to the verification steps and a modified one to the download. That is a strong precondition, which is why this is Low. The payoff is real: the playground is a "verified site" in Presto's registry, so its JavaScript runs with users' standing approval to use the local prover.

The fix. Keep the hash from the step that cryptographically verified the package, hash the downloaded file locally, and refuse to deploy if they differ. Small change, and the same discipline F-001 needs.

Low · informational F-005 Caller-supplied payload iterator runs after the last policy check before dispatch
Found by Codex (Claude verified) confidence: high (mechanism) · low (significance) CWE-367 fix: under an hour · CHEAPEST

What it is. The client re-checks its configuration one last time before sending a proof, so a caller who switches to "HTTPS only" mid-flight is honoured. One step still runs after that check: copying the caller's payload, which for exotic payload types can run caller-provided code. That code could reconfigure the client and the check would not see it.

What an attacker would do. Practically nobody: neither shipped adapter builds such a payload, and the only party who can reach this is a program subverting its own client. Both verifiers agree it is a mechanism, not a risk; one would not band it at all.

The fix. Move the copy above the check. One line, done as part of F-002.

Technical trace

Instances: packages/sdk-core/src/lib/presto-client.ts:385 → :396 → :401 / presto-transport.ts:958.

Cross-cutting observations

Privileged CI steps trust artifacts across an untrusted boundary without a digest

F-001 and F-004 are one pattern in two places: a verification result is produced, then the bytes actually consumed are fetched or mutated separately, and no hash carries the result forward. The release path already knows how to verify (provenance, signatures, --ignore-scripts in one script); what it lacks is the habit of computing a local digest at the trust boundary and asserting it at the sink. Adopt that as a rule for every workflow that publishes or deploys.

Mutable shared client state consulted after a check

PrestoClient.prove() snapshots the request and re-checks a generation counter, but the destination is read live from the transport, which any concurrent attempt can change (F-002), and caller code can still run after the last check (F-005). The rule that closes both: one immutable eligibility-plus-destination snapshot per attempt, and every mutation of shared state bumps a generation the final check compares.

Resource caps bound concurrency and residency, not churn

The app limits how many proofs run at once and how big the cache may grow, but nothing limits rate over time: downloads per hour, activity refreshes per window. F-003 is the instance; the general fix is a token bucket wherever a client can trigger a costly side effect repeatedly.

Side effects before validation

On both prove routes, version resolution (download, cache bookkeeping) runs before the payload is decoded, so the cheapest requests pay the most expensive side effects. The ordering is deliberate for latency; the download budget above makes it safe without reordering.

Containment is best-effort against an adversarial child

Process-group and Job-Object containment is correct for the authentic bb. "Confirmed dead" is a statement about the original group or job, not about every descendant a hostile binary might have spawned. Defense-in-depth options exist (CREATE_SUSPENDED + assign + resume on Windows; child-subreaper or cgroup on Linux) if the trust model ever changes.

The revocation denylist is the only version-safety control and is empty

A compile-time constant in version_policy.rs is the sole lever for refusing a known-bad bb version, and activating it needs a Presto release. That is acceptable today; it is worth knowing that there is no faster path.
