# Cluster audit: bb-child-and-versions

Scope: `packages/presto/core/src/bb.rs`, `bb/ultra_honk.rs`, `versions/{downloader,cache_layout,leases,release_metadata,version_policy}.rs`, `packages/presto/server/src/main.rs`, plus the one-hop callers in `server/{prove.rs, ultra_honk.rs}`.

## Findings

### F-1: No rate limit on triggering a new bb-version download — network/disk/CPU amplification DoS

1. **Title**: Unbounded per-request bb-version download churn allows a single approved origin to sustain network/disk/CPU exhaustion.
2. **Impact factors**: Availability — repeated ~20-40 MB tarball downloads, full-file SHA-256 hashing, gzip-bomb-capped decompression (up to 512 MiB scanned per attempt), a macOS `codesign` subprocess spawn, and a GitHub API round trip, all triggered by a single small HTTP header value. Blast radius is the local machine's network egress, disk I/O, and CPU, degrading or starving legitimate proving for the whole app (single global `prove_semaphore`). Attack vector: network (loopback HTTP from an approved browser origin, or auto-approved localhost). Attack complexity: low — just cycle `x-aztec-version` through valid, unlisted, real historical Aztec release strings. Privileges required: an approved origin (or localhost, auto-approved). User interaction: none once approved.
3. **Evidence confidence**: moderate. The trace is concrete and unconditional; the main uncertainty is real-world severity, which is throttled by GitHub's own unauthenticated API rate limit (see "Why mitigations fail" below).
4. **OWASP / CWE**: OWASP API4:2023 / A05:2021 (Unrestricted Resource Consumption); CWE-400 (Uncontrolled Resource Consumption), CWE-770 (Allocation of Resources Without Limits or Throttling).
5. **Trace**:
   - `x-aztec-version` header (untrusted, attacker/approved-origin controlled) read at `packages/presto/core/src/server/prove.rs:374-379` (`requested_version`).
   - → `acquire_prover` (`server/prove.rs:305-340`), called from both scheme handlers: `server/prove.rs:216` (`/prove`) and `server/ultra_honk.rs:333` (`/prove/ultra-honk`).
   - → `resolve_version` (`server/prove.rs:51-91`) → `parse_selectable_version` (`server/prove.rs:93-106`, charset+semver+empty-denylist check only) → `versions::verify_cached_bb` (`versions/cache_layout.rs:232-252`) decides `needs_download`.
   - → `download_if_needed` (`server/prove.rs:381-409`) → `versions::download_bb` (`versions/downloader.rs:21-60`): `download_tarball` (`versions/downloader.rs:118-152`, network GET up to `MAX_DOWNLOAD_BYTES = 64 MiB`, `versions/downloader.rs:131`) → `verify_digest` (`versions/downloader.rs:158-180`, GitHub API call + full SHA-256) → `install_version_dir` (`versions/downloader.rs:271-364`): `extract_bb_from_tarball` (`versions/downloader.rs:416-467`, decompression capped at `MAX_DECOMPRESSED_BYTES = 512 MiB`, `versions/downloader.rs:387`) → `finalize_downloaded_binary` (macOS `codesign` subprocess, `versions/downloader.rs:66-103`) → `sha256_file` over the final binary (`versions/cache_layout.rs:122-136`).
6. **Missing control**: no per-origin or global rate limiter/cooldown on triggering a *new* version download, and no cap on distinct-versions-downloaded-per-unit-time. `MAX_INFLIGHT_PROVE = 8` (`server.rs:52`) and `MAX_ULTRA_HONK_PER_ORIGIN = 4` (`server/ultra_honk.rs:31`) cap *concurrency*, not sequential throughput; `CACHE_MAX_TOTAL_BYTES = 2 GiB` (`versions/version_policy.rs:197`) bounds steady-state disk residency but not cumulative churn (download → evict → re-download), and the code's own "active window" exemption (`versions/downloader.rs:202-231`, `CACHE_ENTRY_ACTIVE_WINDOW = 5 min`) explicitly lets the cache transiently overshoot the cap within a burst.
7. **Exploit story**: An approved origin's page script sends a burst of `/prove/ultra-honk` (or `/prove`) requests, each with minimal-but-schema-valid bytecode/witness fields and a distinct `x-aztec-version` value drawn from Aztec's long history of real, unlisted nightly/rc/mainnet releases (the project's own comment notes "barretenberg nightlies ship every night"). Each request forces a full download-verify-cache cycle *before* the submitted bytecode/witness content is even decoded (download happens in `acquire_prover`, ahead of the ultra-honk body's gzip decode stage per the route map's step ordering), so the attacker doesn't need valid circuit data at all — just enough bytes to pass JSON/size checks. Four such requests per origin run concurrently; repeating serially sustains continuous disk/network/CPU load.
8. **Preconditions**: origin already approved (or localhost, auto-approved in both desktop and headless-default modes), and enough distinct real Aztec version tags to enumerate (readily available given nightly release cadence).
9. **Why mitigations fail**: The unauthenticated GitHub API digest lookup (`versions/release_metadata.rs:83-120`) is rate-limited by GitHub to ~60 requests/hour per source IP, which is a genuine but *incidental* backstop — not a control this codebase implements, and it still permits a burst of ~60 full downloads (≈1-2 GiB of churn) before it engages, then resets hourly, making the attack sustainable indefinitely at a throttled but nonzero rate. It does not bound the actual tarball GET (`github.com/.../releases/download/...`, a separate, effectively unthrottled CDN path).
10. **Instances**: shared root cause, both scheme handlers: `server/prove.rs:210-228` (`/prove`) and the call at `server/ultra_honk.rs:333` (`/prove/ultra-honk`); both funnel through `acquire_prover`/`resolve_version`/`download_bb` as traced above.

### F-2: No floor on minimum-safe bb version — an approved origin can force execution of any historical, authentic-but-unvetted bb build

1. **Title**: `x-aztec-version` lets a remote (approved) origin select an arbitrary historical bb build with no recency/safety floor, only a manually-maintained, empty-by-default denylist.
2. **Impact factors**: Integrity/availability of the local bb child process — attacker-chosen bytecode/witness (per the audit brief's threat model, "bb itself is a large C++ program; treat a crash or hang as available to the attacker") is fed to whichever historical bb build the attacker names, rather than only the maintainers' currently-shipped, presumably-most-hardened build. This widens the pool of parser/prover code paths exposed to attacker-controlled input to every Aztec release ever published, including builds with since-fixed (but undisclosed-to-this-denylist) memory-safety issues — an n-day/downgrade-style exposure. Attack vector: network (approved browser origin). Attack complexity: low (well-formed semver string). Privileges required: approved origin. User interaction: none once approved.
3. **Evidence confidence**: low-moderate. The trace and missing control are concrete, but no specific CVE in a specific historical `bb` build was verified as part of this review — the finding is the absence of a floor, not a proven exploit against a named old build. The maintainers' own code comments already reason extensively about this trade-off and describe it as a deliberately deferred, reactive control (see below), so treat this as a documented-residual-risk confirmation rather than a novel discovery.
4. **Evidence confidence caveat / OWASP / CWE**: OWASP A06:2021 (Vulnerable and Outdated Components); closest CWE: CWE-1104 (Use of Unmaintained Third Party Components) / CWE-829-adjacent (execution of a component whose trustworthiness at that specific build is not vetted).
5. **Trace**: same ingress as F-1 through `check_version_selectable` (`versions/version_policy.rs:295-297`) → `check_version_against` (`versions/version_policy.rs:302-315`): validates canonical strict semver + no build metadata, then checks only `KNOWN_VULNERABLE_VERSIONS` (`versions/version_policy.rs:249`, **empty by default**) — no minimum-version comparison exists anywhere in this function or its caller. Selected version proceeds to `find_bb(Some(&version))` (`bb.rs:47-92`, cache-only per F-007) and is executed against attacker-supplied bytecode/witness via `run_ultra_honk`/`prove` (`bb/ultra_honk.rs:159-179`, `bb.rs:293-338`).
6. **Missing control**: no minimum-safe-version floor, no automated vulnerability/CVE feed integration; `KNOWN_VULNERABLE_VERSIONS` is a compile-time constant the maintainers must hand-populate reactively per-incident.
7. **Exploit story**: If a memory-corruption bug is later found and fixed in some `bb` release N, an attacker (an approved origin) can still request Aztec version N-1 (or any earlier one not added to the denylist) via `x-aztec-version`, pair it with a crafted circuit designed to trigger the known-fixed bug, and get the vulnerable code path executed locally — unless and until the maintainers manually add that exact version string to `KNOWN_VULNERABLE_VERSIONS` and ship a new presto release.
8. **Preconditions**: a real, disclosed (or discovered) memory-safety bug in some historical `bb` build reachable via the exposed `prove`/`ultra_honk` CLI surface; origin approval.
9. **Why mitigations fail**: digest verification (SEC-02, already documented in `versions/release_metadata.rs:73-82`) only proves the downloaded binary is the *authentic*, unmodified release for that version — it says nothing about whether that version is *safe*. The revocation list is reactive and manual, and the code's own comments (`versions/version_policy.rs:238-249, 277-294`) explain why a simple newer-is-safer floor was rejected (many Aztec versions share one `bb`, so a floor would break legitimate older-but-compatible dApps) without proposing an interim mitigation beyond the empty denylist.
10. **Instances**: single control point, `versions/version_policy.rs:295-315`; reached identically by both `/prove` and `/prove/ultra-honk` via `server/prove.rs:93-106`.

## Non-findings considered

- Command injection via bb argv: all args are literals or validated/tempdir-derived paths passed through `Command::args` (no shell); `verifier_target` is a closed enum (`bb/ultra_honk.rs:31-98`) — not reachable.
- Path traversal via `x-aztec-version`: `is_valid_version` (`versions/version_policy.rs:321-330`) rejects `..`, leading/trailing dot, non-alnum/`.-_` chars; `AztecVersion` is the only type that reaches path/URL-building sinks — checked, closed.
- Zip-slip / tar-path traversal in `extract_bb_from_tarball`: extraction target is always `dest.join(bb_binary_name())`, ignoring the tar entry's own embedded path; only `EntryType::Regular` accepted (symlink/hardlink entries rejected) — checked, closed (test: `extract_bb_rejects_symlink_entry`).
- TOCTOU on the prove workspace / witness files: directories created `0700` and files `0600`/DACL-protected at the creation syscall (never create-then-chmod), `create_new(true)` fail-closed on Unix — checked, closed.
- Reap-orphaned-workspaces as an arbitrary-delete primitive: `symlink_metadata` (never follows links), fixed `prove-` prefix, floor of 24h — checked, closed (test: `reap_does_not_follow_symlinks_out_of_the_parent`).
- Publisher-vs-executor race on first-time version install (two concurrent downloads of a brand-new version both attempt `rename` into an empty slot): OS-level `rename` semantics fail the loser (non-empty-dir/exists), which then surfaces as a benign download error, not data corruption — checked, not a security issue.
- GitHub API JSON response unbounded read (`fetch_github_asset_digest`, no explicit size cap on `.json()`): only exploitable if GitHub's control plane itself is compromised or MITM'd, which is the same precondition as the already-documented SEC-02 circular-trust caveat (`versions/release_metadata.rs:73-82`) — not a new path, not reported separately.
- Windows text-mode client-vk handling silently substituting a bb-computed key: covered by the excluded, documented trust boundary ("a client-supplied verification key can only spoil that client's own proof").
- Quiesce/containment race windows (Unix pgid, Windows Job Object) around update installs: extensively hardened with atomic spawn+register-under-lock, fail-closed poisoning on unconfirmed kills, and dedicated regression tests for every previously-found race (`bb.rs:603-1030`) — reviewed, no new gap found within the interprocedural cap of this pass.

## Out of cluster

- `server/auth.rs:80-84` documents that a request with **no** `Origin` header is treated as `Approval::ungated()` ("auth bypass by design for non-browser callers"); this interacts with the headless server's `ALLOWED_ORIGINS` gating story but is squarely inside the auth/origin cluster's scope, not this one — flagging only as a pointer in case that cluster's agent wants to cross-check it against `bb-child-and-versions`' download/lease path.

## Cross-rebuttal

### (1) What Codex missed

Nothing new. Codex's F-1 (cache-size-cap defeat via activity-window refresh) and F-2 (FIFO-blocks-the-permit) independently corroborate the same two attack surfaces this report already covers (unbounded version-cache churn; the C++ bb child as an availability sink) from different, complementary angles. No additional concrete, in-scope, novel source→sink trace was found while verifying their report.

### (2) Verdicts on Codex's findings

**F-1 (cache-size cleanup bypass via activity-window refresh): VERIFIED.** Traced and confirmed independently: `prove.rs:82` (`verify_cached_bb`) → `cache_layout.rs:249` (`mark_in_use`) → `cache_layout.rs:271-275` (remove+rewrite `.last-used`, bumping the dir's mtime) runs on **every** `resolve_version` call for an already-cached version, *before* bytecode/witness content is validated (confirmed: `acquire_prover` at `ultra_honk.rs:333` precedes `decode_and_check` at `ultra_honk.rs:338`, so a request that will later fail on garbage content still refreshes activity). `evict_if_unheld` (`version_policy.rs:413-417`) treats any `recently_active` dir as un-evictable, and the one scheduled retry (`cleanup_after_active_window`, `version_policy.rs:463-479`) does not reschedule itself if it also finds versions active (`version_policy.rs:477` discards the deferred-bool return). All cited line numbers check out against the current source. This is a real, no-malicious-bb-required finding — it does not depend on a compromised release at all, only on ordinary (if abusive) client requests against the official, digest-verified binary, so it is squarely in scope. It is a sharper mechanism than — and subsumes — this report's own F-1 (see part 3).

**F-2 (FIFO blocks the global prove permit): VERIFIED as a code-level claim.** `bb.rs:487` (`std::fs::File::open(path)?` inside `read_capped`) is indeed a blocking open with no `O_NONBLOCK`, reachable from `read_fields` (`bb/ultra_honk.rs:315`) → `read_outputs` (`bb/ultra_honk.rs:409-410`) → the output-read worker (`ultra_honk.rs:365-368`). Confirmed by direct read of `server/ultra_honk.rs:365`: `on_worker(held, move |_| { bb::read_ultra_honk_outputs(&workspace)... })` — the closure's cancellation-flag parameter is bound to `_` and never polled, so even a client-disconnect (`CancelOnDrop`, `ultra_honk.rs:267-274`) cannot unstick a blocked worker; `PROVE_TIMEOUT` only bounds `child.wait()` (`bb.rs:359`), not this later file read. Technically sound. **Malicious-bb precondition: OUTSIDE this audit's in-scope trust model.** It requires bb's own output directory to contain a FIFO instead of a regular file — unreachable via crafted Noir bytecode/witness against the *official* binary. The only ways to get there are (a) the documented SEC-02 circular-trust compromise of Aztec's GitHub release pipeline, which this report and Codex's own non-findings section both already exclude as pre-tracked, or (b) an operator-set `BB_BINARY_PATH` override, which `bb.rs:34-35` documents as "the one documented exception to 'no unverified execution': whoever sets the process env already owns the process" — i.e., the same-user-malware exclusion this audit's brief names explicitly. Reporting F-2 as a finding while separately excluding SEC-02 in the non-findings section is an internal inconsistency: both share the identical precondition.

**F-3 (Windows ordinary exit leaves descendants running): VERIFIED, same out-of-scope precondition.** Confirmed: `Guard::finish()` on Windows (`bb.rs:929-931`) only sets `armed = false` and never calls `TerminateJobObject`, unlike the Unix `finish()` which SIGKILLs the whole group even on the success path (`bb.rs:679-687`, matching the `finish_reaps_a_straggler_grandchild_on_the_success_path` test). A real Unix/Windows asymmetry, but only observable if bb forks a surviving worker — malicious-bb-only, same as F-2.

**F-4 (Unix `setsid()` escape from the process group): VERIFIED, same out-of-scope precondition.** `containment::configure` only sets `process_group(0)` at spawn (`bb.rs:626-628`); nothing prevents a *descendant* from calling `setsid()` to leave that group, and `kill(-pgid, ...)` (`bb.rs:683,697,709,723`) only reaches processes still in it. Correct, well-known Unix containment limitation — but requires bb itself (or a process it spawns) to deliberately evade, i.e., malicious-bb-only.

**F-5 (Windows pre-assignment execution window): VERIFIED, same out-of-scope precondition.** `spawn_capturing_stderr` (`bb.rs:894`) starts the process before `AssignProcessToJobObject` (`bb.rs:906`) runs — a genuine gap, since this code has no suspended-create+assign+resume sequence. Real Windows Job Object limitation, but exploiting it requires bb to race its own assignment with malicious intent — malicious-bb-only.

### (3) Revisions to this report's own findings

**F-1 (download-churn DoS) — strengthened, not withdrawn.** Codex's F-1 sharpens the missing control I identified: the bottleneck isn't only "no rate limit on triggering a *new* download," it's specifically that `mark_in_use`'s activity-window refresh can be triggered by cheap, ultimately-invalid requests against *already-cached* versions, letting an attacker hold the cache over `CACHE_MAX_TOTAL_BYTES` indefinitely without any further downloads at all once the initial burst fills it. I'm folding this into F-1's "missing control" as the more precise mechanism; confidence moves from moderate to effectively corroborated by independent analysis.

**F-2 (no minimum-safe-version floor) — unchanged.** Not addressed by Codex's report either way; stands as originally reported at low-moderate confidence.
