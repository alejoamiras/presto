# Cluster audit: `playground-noir` (`packages/playground`) — Claude

Scope read in full: `packages/playground/src/noir.ts`, `src/noir-stub.ts`, `src/main.ts` (noir-btn handler, `setActionButtonsDisabled`, `walletReady`, HTTP-consent flow), `src/results.ts`, `src/ui.ts`, `index.html`, `vite.config.ts`, `public/_headers`, `wrangler.jsonc`; `src/aztec.ts` limited to its `httpsOnly`/`forceProofs` query-param reads. Handoff edge followed one function deep: `PrestoUltraHonkBackend` (`packages/sdk-noir/src/lib/presto-ultra-honk-backend.ts`) constructor + `generateProof`.

## Findings

None. No reachable source→sink path was found in this cluster that lets an untrusted or over-privileged actor violate confidentiality, integrity, authorization, or availability, beyond the already-documented/accepted trust boundaries.

## Non-findings considered

- **DOM XSS via rendered proof/error strings**: `results.ts:showResult` (`file:playground/src/results.ts:144-166`) and `ui.ts:appendLog` (`file:playground/src/ui.ts:33-65`) exclusively use `textContent`/`createElement`, never `innerHTML`/`insertAdjacentHTML`/`document.write`/`eval`. Grep across `packages/playground/src` and `index.html` for `innerHTML|outerHTML|document.write|eval(|new Function|insertAdjacentHTML` found zero hits in production code (only in test setup/teardown, e.g. `src/ui.test.ts:34`). `err.message` from a failed Noir proof (`main.ts:192`) reaches `appendLog` only as `line.textContent`, so attacker-influenced error text (e.g. from a malicious local presto) cannot inject markup. Not a finding.
- **Query-param handling (`noirStub`, `httpsOnly`)**: both read via strict `=== "true"` string compare (`noir.ts:115`, `:119`) and never reflected into the DOM — they only gate boolean backend construction. `noirStub` is additionally gated by `import.meta.env.DEV` (`noir.ts:119`), a compile-time constant that Rollup dead-code-eliminates in production, corroborated by `e2e/noir.production-smoke.spec.ts` asserting real WASM traffic occurs even with `?noirStub=true` on the built bundle. Not a finding.
- **HTTP-session consent leaking into the Noir backend**: `getNoirBackend()` (`noir.ts:107-128`) builds an independent `PrestoUltraHonkBackend`/`PrestoClient`; the code comment (`noir.ts:101-106`) and the absence of any wiring from `httpSessionConsent`/`enableInsecureHttpForSession` (`main.ts:67-101`) into `noir.ts` confirm the Aztec prover's HTTP-session opt-in does not reconfigure the Noir backend's transport. `httpsOnly` is only ever set to `true` (stricter) via the URL knob (`noir.ts:124`); there is no `httpsOnly=false` switch (confirmed by the comment at `aztec.ts:110`). No code path in this cluster forces a plaintext `/prove/ultra-honk` send. The default (no query param) delegates to `PrestoClient`'s own transport policy, which lives in `sdk-core` — out of this cluster's file list and not re-verified here (see repo map's cluster boundary).
- **Malicious/local presto response handling**: `noir.ts` only compares response bytes for a UI label (`matchesFixture`/`same`, `noir.ts:61-82`) after `PrestoUltraHonkBackend.generateProof` has already decoded/validated the response (`presto-ultra-honk-backend.ts:135-144`, `decodeUltraHonkResponse`). No trust decision in the playground cluster itself depends on unvalidated server bytes. Already-documented boundary (shape-matched discovery, not authenticated) — no new path found.
- **Prototype-pollution via `bbWorkerPlugin` dev middleware**: `vite.config.ts:58-75` looks up `req.url`'s basename against a fixed 3-entry map using `Object.hasOwn`, explicitly to dodge `"constructor"`/`__proto__`-style basenames; the redirect target is one of three `require.resolve()`-derived absolute paths fixed at server start, not attacker-influenced. Dev-server only. Not a finding.
- **`fs.allow: ["../.."]` / dev-server file exposure** (`vite.config.ts:216-218`): widens (or, more likely, is a no-op restatement of) the Vite dev-server's allowed static-file root to the Bun-workspace root, needed because `vite.config.ts` reads `../sdk/package.json` and `noirFixturePlugin` reads `../../fixtures/noir/square/*`. Since the monorepo already has a root-level `bun.lock`, Vite's own workspace-root auto-detection would already include this same root by default. Dev-server only (not shipped in `dist/`), and any generic Vite dev-server traversal/DNS-rebinding CVE class is out of scope here per the brief ("Outdated packages with known CVEs: flagged for separate dependency-audit verification"). Not a finding.
- **Playground as a "verified" origin in Presto's site registry**: the threat model asks what a cross-origin page can do by abusing the playground's verified status. Nothing in this cluster's code (no injection sink, no over-broad postMessage/BroadcastChannel listener, no `window.opener` handoff) gives another origin a way to execute inside `playground.presto.build`'s context or to piggyback on its approval. The registry/approval semantics themselves live in the Presto Rust app, outside this cluster's files — not re-verified here.
- **Third-party resources in `index.html`**: only Google Fonts stylesheet links (`fonts.googleapis.com`/`fonts.gstatic.com`) and plain anchors to `presto.build`/`github.com` (not fetched by JS, `target="_blank" rel="noopener noreferrer"` set). No third-party `<script>` tags. Not a finding.
- **CSP absence**: confirmed no `Content-Security-Policy` anywhere in `public/_headers`, `vite.config.ts` dev/preview headers, or `index.html`. Since no DOM sink accepts untrusted HTML/script in this cluster (see above), there is no concrete bypass to demonstrate; per the brief, "framework-default protections... UNLESS you can show a concrete bypass" are not flagged. Noted as a defense-in-depth gap only, not a finding.
- **Log/DoS via unbounded growth**: `appendLog` (`ui.ts:33-65`) caps the in-DOM log at 500 entries, evicting the oldest. `#noir-btn`'s handler (`main.ts:165-203`) sets `deploying = true` and disables the button for the duration of a proof, preventing concurrent-click resource exhaustion from this cluster's UI. Not a finding.
- **Non-constant-time byte comparison** (`noir.ts:61-62`, `same()`): compares public proof/public-input bytes for a UI "identical/differs" label, not a secret or an authorization decision — timing side-channels are inapplicable. Not a finding.
- **Verifier-target confusion**: the fixture's `verifierTarget` (from `manifest.json` via `virtual:noir-fixture`) is used consistently for both the seeded verification key and the `generateProof` call (`noir.ts:122-123`, `:149-151`) — same fixture object, no mismatch path. Not a finding.
- **Open redirect via `appendLog`'s `url` param**: mechanism exists (`ui.ts:45-53`, safe `href`/`textContent` construction with `rel="noopener noreferrer"`) but per the repo map is never invoked from any Noir code path in this cluster. Not a finding.
- **CORS / cache poisoning**: this cluster ships a static SPA (Cloudflare Workers Static Assets, `wrangler.jsonc:8-11`) with no server-side logic and no CORS headers of its own; `_headers` only sets COOP/COEP/`X-Content-Type-Options`/`Referrer-Policy` plus narrow `Cache-Control` overrides for two WASM-adjacent assets and `index.html`. No cache-key or CORS misconfiguration surface exists in this cluster. Not a finding.

## Out of cluster

- None serious enough to flag; everything of note traces back into `sdk-core`'s `PrestoClient` transport policy or the Presto desktop app's site-authorization/verified-sites registry, both explicitly outside this cluster's file list.
