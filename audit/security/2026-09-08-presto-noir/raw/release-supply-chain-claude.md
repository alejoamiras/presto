# Security audit — cluster: release-supply-chain

## Findings

### F-1: Untrusted npm lifecycle scripts run inside the OIDC-privileged publish job, exposing the trusted-publish token and a `contents: write` git credential

**Impact factors**: A supply-chain-compromised transitive npm dependency, resolved fresh (not through `bun.lock`) during the publish job's consumer-verification steps, executes with the ambient `ACTIONS_ID_TOKEN_REQUEST_URL`/`ACTIONS_ID_TOKEN_REQUEST_TOKEN` environment variables and the checkout-persisted `contents: write` git credential available to every step of that job. A malicious `postinstall` script can mint a fresh OIDC token asserting this repo/workflow's identity (the same identity npm's trusted-publishing feature relies on for `@alejoamiras/presto`/`presto-core`/`presto-noir`) and either exfiltrate it or use it directly to publish an attacker-controlled package/version under this org's trusted-publisher relationship, and/or `git push` using the persisted token. Confidentiality and integrity impact is high (forged npm publish, possible malicious git push); blast radius covers the entire release identity for all three packages. Attack vector is network-originated (a compromised package pulled from the public registry) but attack complexity is high — it requires an actual upstream supply-chain compromise to be live at the moment of a release run. No privileges are required of the ultimate attacker beyond that compromise; no user interaction is needed once a maintainer dispatches a real release.

**Evidence confidence**: high (the GitHub Actions `id-token: write` → ambient token-env-var-for-the-whole-job behavior and `persist-credentials: true` default are documented platform behavior; the missing `--ignore-scripts` flag is directly observed in the file). Moderate on end-to-end exploitability, which additionally requires a live upstream compromise as precondition.

**OWASP / CWE mapping**: OWASP A08:2021 (Software and Data Integrity Failures), also A05:2021 (Security Misconfiguration — overly broad credential exposure); CWE-829 (Inclusion of Functionality from Untrusted Control Sphere), current CWE Top 25.

**Trace** (source → sink):
1. `.github/workflows/_publish-npm.yml:43-45` — the `publish` job requests `permissions: id-token: write` and `contents: write`. GitHub Actions injects `ACTIONS_ID_TOKEN_REQUEST_URL`/`ACTIONS_ID_TOKEN_REQUEST_TOKEN` into **every** step's environment for the life of this job (not just the step that later uses them).
2. `.github/workflows/_publish-npm.yml:52-54` — `actions/checkout` runs with default `persist-credentials: true` (no override), so `.git/config` in the job workspace carries a `contents: write`-scoped credential helper usable by any process in the job, including `git push`.
3. `.github/workflows/_publish-npm.yml:161-162` — "Test the exact publish artifact as an npm consumer" runs `bash scripts/sdk-tarball-consumer.sh "$TARBALL" "$PACKAGE"`.
4. `scripts/sdk-tarball-consumer.sh:79` — `( cd "$EXACT" && npm install --no-audit --no-fund --loglevel=error )`: a plain npm install, scripts **enabled**, of a host `package.json` built by `scripts/tarball-consumer/host-manifest.ts` from the packed candidate's real, range-based dependencies (e.g. `@logtape/logtape: ^2.3.2`) — resolved fresh against the live registry, independent of `bun.lock`.
5. `scripts/sdk-tarball-consumer.sh:111` — the same unscoped `npm install` for the "conflict host" (reached for the `presto` package, which carries `@aztec/stdlib`).
6. `.github/workflows/_publish-npm.yml:245` — "Verify release records and a fresh registry install" runs `npm install --no-audit --no-fund --loglevel=error "$PACKAGE_NAME@$VERSION"` in a temp dir, again without `--ignore-scripts`, still inside the same `id-token: write` job.
7. Sink: any package's lifecycle script executed by steps 4–6 can read `ACTIONS_ID_TOKEN_REQUEST_TOKEN`/`_URL` (mint an OIDC token for any audience, including npm's trusted-publishing audience) and/or read the persisted git credential from step 2, and exfiltrate or use either.

**Missing control**: none of the three `npm install` invocations above pass `--ignore-scripts`, and none of them run in a job/step scoped without `id-token: write`/`contents: write`. There is no isolation between "run code from a package I'm testing" and "hold the credentials that can publish under this identity."

**Exploit story**: A maintainer dispatches `release-sdk.yml` to publish `presto-noir`. The `publish` job starts with the OIDC/git credentials described above already ambient. `bun install --frozen-lockfile` resolves the locked graph (comparatively protected — see "why mitigations fail"). The "Test the exact publish artifact as an npm consumer" step then builds a fresh host and runs unscoped `npm install`, resolving whatever the registry serves right now for the candidate's real dependency ranges. If one of those packages (or a newly-resolved transitive dependency not exact-pinned) carries a malicious `postinstall` at that moment, it runs with the step's environment, mints an OIDC token via the well-known `curl "$ACTIONS_ID_TOKEN_REQUEST_URL&audience=..." -H "Authorization: bearer $ACTIONS_ID_TOKEN_REQUEST_TOKEN"` pattern, and either exfiltrates it or immediately calls `npm publish` with it, or uses the persisted git credential to push. Every downstream check this pipeline runs afterward (its own tarball-consumer pass, provenance/signature re-verification) inspects the *legitimate* artifact the "official" `npm publish` step publishes moments later — none of it detects the rogue action already taken with the stolen token, because that action happens outside the code paths those checks look at.

**Preconditions**: (a) a real release run is dispatched from `main` by an authorized maintainer — legitimate use of the pipeline is what opens the window, no separate attacker action is needed to reach the vulnerable steps; (b) at least one package resolved fresh by the affected `npm install` calls is compromised at that moment (a supply-chain precondition this cluster's own threat model names explicitly).

**Why mitigations fail**: Bun's default script-blocking (no `trustedDependencies` needed to protect `bun install --frozen-lockfile`, confirmed absent from `bunfig.toml`/`package.json`) does not apply — the three installs above use plain `npm`, not `bun`. The `bunfig.toml:17` 7-day `minimumReleaseAge` quarantine is explicitly scoped ("Affects dependency RESOLUTION (`bun add`/`bun update`)... `bun install --frozen-lockfile`... unaffected") and does not gate the range-based `npm install` these scripts perform against the live registry. `scripts/verify-sdk-package-signatures.ts:51` already passes `--ignore-scripts` for its own, separate `npm install` — proof the team is aware of this exact risk class — but that protection is local to that one script and does not cover the three instances below. Per-step `env: GH_TOKEN` blocks elsewhere in the same workflow limit which steps can read `github.token` through that specific variable, but do not limit the job-wide `ACTIONS_ID_TOKEN_REQUEST_*` variables or the checkout-persisted git credential, neither of which is gated by step-level `env:` at all.

**Instances** (same root cause — unscripted npm installs inside the `id-token: write` + `contents: write` `publish` job):
- `scripts/sdk-tarball-consumer.sh:79` (exact-host install; runs for every published package)
- `scripts/sdk-tarball-consumer.sh:111` (conflict-host install; `presto` only)
- `.github/workflows/_publish-npm.yml:245` (final fresh-registry install)
- Enabling grants: `.github/workflows/_publish-npm.yml:43-45` (job `permissions`), `:52-54` (default `persist-credentials: true`)

Note: `scripts/sdk-tarball-consumer.sh` is also invoked from `.github/workflows/_ts-package-ci.yml`'s `tarball-consumer` job (PR-gate CI), but that job has no `permissions:` override and inherits the workflow-level `contents: read` only (`_ts-package-ci.yml:30-31`) — no `id-token: write` there, so that call site is **not** an instance of this issue.

## Non-findings considered

- Workflow injection via `${{ }}` in `run:`: every interpolated value across all six workflow files is routed through an `env:` variable first, never spliced directly into a script body; no bypass found.
- Unpinned third-party GitHub Actions: every `uses:` in the read workflows is pinned by full commit SHA with a version comment; no finding.
- `workflow_dispatch` inputs (`packages`, `mode`, `dry_run`) reaching a shell/script unsafely: all flow through `env:` vars into `release-plan.ts`, which fails closed via `isPackageKey`; an off-enum raw API dispatch cannot bypass this.
- `dependency_versions`/`version` handoff from `plan` to `_publish-npm.yml`: bound by `EXACT_SEMVER.test()` in `prepare-sdk-publish.ts:70-73` before being written into any manifest; not shell-injectable (passed via `env:`, read into a bash array).
- Provenance subject-digest check being an optional parameter in `verifyProvenanceStatement`: its only production caller, `fetchAndVerifySdkProvenance`, always supplies `expectedSha512` (`sdk-release-verification.ts:117-133`); no call path skips it.
- Bypassing the `assert-main` (main-only) gate via a modified `release-sdk.yml` dispatched from a feature branch: downstream publish jobs key off `needs.plan.outputs.*`, which are empty when `plan` is skipped (transitively, since `plan` requires `assert-main` to succeed); the `if:` conditions in `release-sdk.yml` check these outputs explicitly, so a skipped `assert-main` cannot silently fall through to a publish job as currently written.
- Whether GitHub's OIDC/npm-provenance claims record the top-level `release-sdk.yml` path or the reusable `_publish-npm.yml` path for `workflow.path` (checked against `sdk-release-verification.ts`'s `SDK_RELEASE_WORKFLOW` allow-list): could not confirm from repository contents alone which path GitHub/npm actually embeds for a job executing inside a called reusable workflow; not asserted as a finding per the "do not speculate" instruction.
- `tar -xzf --strip-components=1` extraction in `packaged-e2e-swap-sdk.sh`/publish flow as a zip-slip/symlink-escape vector: every tarball extracted is either just built by the same job from trusted source, or a provenance-and-integrity-verified published tarball; no lower-trust actor supplies these archives.
- CI "Upload presto log" artifact potentially leaking witness/secret data (`_ts-package-ci.yml:246-253`): per the `route-ultra-honk` map's documented behavior, only lengths/metadata are logged and bb's stderr is captured server-side and never returned to clients or logged in full — the underlying server code is outside this cluster's file list to verify further, but no concrete leak path was found from the files available here.
- TOCTOU in `promote-sdk-latest.ts`'s `npm dist-tag add` (no compare-and-swap API): explicitly self-documented and narrowed (re-checks immediately before the mutation, `promote-sdk-latest.ts:234-237`); the racing actor would need to be another npm-publish-privileged party, not an untrusted one, and the script is human/CLI-invoked, not wired into any CI trigger read in this cluster.
- Untrusted registry/GitHub API JSON (`npm view`, `gh release view`) reaching a shell: always `JSON.parse`'d and consumed as data (comparisons, planning decisions), never passed to `eval` or interpolated into a command string.

## Out of cluster

- None of notable severity observed beyond this cluster's files; the presto-server request-handling/logging code referenced by the CI log-artifact concern belongs to the `route-ultra-honk` cluster and appears independently hardened per its repo map.

## Cross-rebuttal

**(1) What the other reviewer missed.** Codex's F-1 mentions "the hook can use the job's publishing identity directly" as one throwaway sentence, with no trace to the actual mechanism: it never names `ACTIONS_ID_TOKEN_REQUEST_URL`/`ACTIONS_ID_TOKEN_REQUEST_TOKEN` (the ambient OIDC-minting env vars every step gets once a job holds `id-token: write`) or `actions/checkout`'s default `persist-credentials: true` (the `contents: write` git credential left in `.git/config` for any process in the job). Both are concrete, file:line-traceable mechanisms in my F-1 that Codex's report does not develop. Codex also doesn't note that `_ts-package-ci.yml`'s `tarball-consumer` job — which runs the *same* `sdk-tarball-consumer.sh` on every PR — has no `id-token: write` (`_ts-package-ci.yml:30-31`), so the credential-theft sub-vector is scoped to the publish job only; their instance list doesn't draw this line. Conversely, my own report flagged a question Codex's doesn't raise: whether GitHub's OIDC/npm-provenance `workflow.path` claim for a job inside a *called* reusable workflow (`_publish-npm.yml`) actually equals the hardcoded `SDK_RELEASE_WORKFLOW = "release-sdk.yml"` (`sdk-release-verification.ts:10`) that gates reuse/promotion — neither of us could confirm this from repo contents, but I logged it as an open question rather than staying silent on it.

**(2) Verdicts.**

*Codex F-1 (registry dependencies execute with publishing privileges): VERIFIED, and stronger than stated.* I independently confirmed every cited line: `_publish-npm.yml:158` (`echo "TARBALL=$tarball" >> "$GITHUB_ENV"`) exports the packed candidate's absolute path as a job-wide env var; `sdk-tarball-consumer.sh:79` runs unscoped `npm install` in a later step of the *same* job; `_publish-npm.yml:167` later runs `npm publish "$TARBALL" --provenance ...` against that same mutable path. Because `TARBALL` is inherited by every child process of that later `npm install` — including a malicious dependency's `postinstall` script — the attack requires no race and no token theft: the hook can simply overwrite the file at `$TARBALL` synchronously during `sdk-tarball-consumer.sh`, and the "Publish" step, running minutes later, publishes whatever is at that path. This is a cleaner, more reliable exploit than the OIDC-theft path I described, sharing the same root cause and the same instance set. I also verified `sdk-tarball-consumer.sh:93` (`npx --yes --package=typescript@5.9 tsc`, an unpinned-patch registry fetch+execute) and `:96` (`node runtime-check.mjs`, which `import`s the freshly-installed dependency graph) as accurate, additional instances.

*Codex F-2 (verified provenance not bound to the deployed tarball): VERIFIED as a code-level gap.* I confirmed `VerifiedProvenance` (`sdk-release-verification.ts:37-42`) and `verifySdkPackageSignatures`'s return type (`verify-sdk-package-signatures.ts:39`, returns `void`) carry no digest out of the verification calls; `published-playground.ts:103-104` verify provenance/signatures, then `:106-111` perform an *independent* `npm pack --ignore-scripts` plus a fresh `npm view dist.integrity` call, comparing the two latest responses to each other — never to the digest actually checked against the provenance subject at `sdk-release-verification.ts:113,117-118`. The extraction sinks (`packaged-e2e-swap-sdk.sh:71,85,134`) and deploy steps (`release-sdk.yml:232,238`) are correctly cited. On the specific question asked: **the "compromised registry serves different bytes to successive requests" precondition is not realistic under this cluster's own threat model.** npm tarball URLs are version-keyed, not content-addressed, but npm's registry treats a published version's bytes as immutable once published (republishing the same version is rejected), and every request here is a `registry.npmjs.org` HTTPS call. Making `npm pack` (line 107) return different bytes than `npm view dist.integrity` reported minutes earlier at line 111 — while that same-moment `dist.integrity` call *also* returns a matching (but different-from-provenance) digest — requires compromising npm's registry/CDN storage layer itself or defeating TLS via MITM, not merely compromising one third-party dependency's publish credentials (F-1's, and this cluster's, assumed attacker capability). That is a materially higher bar than Codex's own "high complexity" label suggests; I'd rate the precondition low-likelihood, though the missing digest-binding is still a real code defect independent of whether that precondition ever holds — a synchronization bug (npm serving genuinely inconsistent bytes to legitimate rapid requests) is more plausible than a targeted attack here.

**(3) Revisions to my own finding.** I'm folding Codex's artifact-substitution variant into F-1 as the primary, higher-confidence exploit path (no timing race needed, no token use required) alongside my original credential-theft path — same root cause, same job, same missing isolation. Added instances: `sdk-tarball-consumer.sh:93` (npx typescript, unpinned patch) and `:96` (require-time execution of the installed graph); added enabling/sink pair `_publish-npm.yml:158` → `:167` for the substitution variant. I'm also narrowing my proposed "missing control": `--ignore-scripts` alone is insufficient, since `runtime-check.mjs`'s `import`/`require` of the installed tree (line 96) executes module-level code regardless of that flag — the real fix is either re-hashing `$TARBALL` immediately before `npm publish` against a digest captured before the untrusted-install step, or moving consumer verification to a job without `id-token`/`contents: write` and passing only a verified digest forward (the same missing-digest-binding pattern as Codex's F-2). I additionally learned from `docs/RELEASE_RUNBOOK.md:18` (outside my assigned file list, checked while verifying Codex's non-findings) that the `npm-publish` GitHub Environment restricts deployment branches to `main`, which is a genuine second, platform-enforced gate behind the in-repo `assert-main` check — this doesn't change F-1, but it does further narrow the non-main-dispatch scenario I had left as an open non-finding.
